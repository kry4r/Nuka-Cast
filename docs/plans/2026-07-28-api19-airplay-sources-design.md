# API 19、AirPlay 与多仓源修复设计

## 目标

在 SHARP Android 4.4.2 / API 19、`armeabi-v7a`、256 MB 应用内存环境中恢复稳定启动，改善 iPhone 16 / iOS 26.5.2 镜像黑屏问题，并让单仓、多仓、直播源和 HTTPS 配置具备可诊断、可恢复的完整工作流。

## 已确认问题

- 0.3.0 全新安装后在目标 ARM 电视启动闪退，但相同代码可在 API 19 x86 模拟器启动，故风险集中在 ARM 原生启动路径和启动时一次性初始化的组件。
- 饭太硬当前上游会返回 HTTP 502；此外主页加载会吞掉逐站点异常，导致“配置成功但主页为空”。
- 0.3.0 要求 Spider JAR 必须使用 HTTPS 并携带 SHA-256，和常见的 HTTP、`;md5;...` 及无摘要 TVBox 配置不兼容。
- Android 4.4 默认 TLS 能力会以 TLS 1.0 发起部分连接，上游要求 TLS 1.2 时会返回 `tlsv1 alert protocol version`。
- 当前配置模型只识别单仓。`{"urls":[...]}` 多仓会被当成站点数为零的单仓并误报解析成功；带 BOM 或开头 `//` 注释的单仓也无法稳定解析。
- 网页各页面各自维护源状态，后台刷新又是异步的，因此配置和直播源变更不会统一触发重新加载。
- AirPlay 已建立会话但画面为黑屏。现有诊断只统计收到和丢弃的包，无法区分握手、解密、SPS/PPS、IDR、MediaCodec 输入和解码输出阶段。

## 源与多仓架构

配置解析分为“配置信封识别”和“单仓内容解析”两层。信封识别负责去除 UTF-8 BOM、前导行注释和支持现有 Base64 包装，然后判定响应为单仓或包含 `urls` 的多仓目录。

多仓作为父源保存，每个 `name`/`url` 条目保存为带父源 ID 的子仓。子仓 URL 规范化后去重，并设置数量上限，防止异常目录耗尽 API 19 内存。导入后立即返回父源与子仓清单，子仓配置在后台以最多两个并发任务刷新。删除父源时一并删除其子仓和缓存；刷新父源时对新增、保留和删除的子仓做差量同步。

“自动合并”表示所有子仓都进入可选仓库集合，而不是同时向所有子仓和所有站点发起搜索。搜索请求先返回按健康状态和历史响应延迟排序的仓库列表，并默认查询最快的健康仓。用户切换仓库时复用关键词并按需搜索该仓。这样既满足搜索后选仓，又避免几十个子仓在 256 MB 设备上制造数百个并发请求。

仓库健康度记录最近刷新结果、站点数、直播源数、失败阶段、最后成功时间和指数移动平均延迟。排序优先级为可用、近期成功、延迟较低，用户手动选择始终覆盖自动排序。

## 网络与 Spider 兼容

共享 HTTP 栈在 API 16-19 显式为 SSL Socket 启用 TLS 1.2，同时保留 OkHttp 的现代与兼容连接规格。不把 HTTPS 自动降级成 HTTP。失败记录主机、TLS 阶段、异常类型和简化错误，避免把敏感查询参数写入诊断。

Spider 引用支持 `;md5;<hash>`、`;sha256;<hash>`、`sha256=<hash>` 和无摘要格式。声明摘要时必须校验；无摘要时使用首次信任并保存内容指纹，后续内容变化标记为需要确认。用户主动添加的 HTTP 配置可以加载，但在诊断中标记明文传输，不再因为强制 HTTPS 直接让所有标准源失效。

主页和搜索不再吞掉站点异常。每个站点记录配置解析、JAR 下载、Spider 初始化、首页调用和结果解析阶段，主页可以返回部分结果，同时报告失败站点数。

## 启动稳定性

应用启动阶段只构造轻量状态和持久化对象。SMB、ExoPlayer、Spider、音视频渲染线程和原生 AirPlay 服务改为按需或服务启动时初始化，单个可选组件失败不会阻止主界面出现。

AirPlay ARM 生命周期先恢复到 0.2.5 已能启动的基线，再逐项重新应用 0.3.0 的生命周期修复。原生库加载、原生服务启动和 mDNS 发布前后写入持久化阶段标记；如果发生无法被 Java 捕获的原生崩溃，下次启动可显示最后到达的阶段。

设备提示改为“应用最低支持 API 17；当前设备 API 19”，不再把 API 17 描述成目标设备。

## AirPlay 视频路径

接收层统一把 iOS 的 AVCDecoderConfigurationRecord 和长度前缀 NAL 转成可验证的 Annex-B 数据。会话保存最近一组有效 SPS/PPS 和 IDR，在 Surface 重建或解码器切换后重新提交配置并等待关键帧。

解码诊断分别统计：镜像连接、已解密负载、配置包、SPS/PPS、IDR、普通帧、MediaCodec 输入、输出格式变化、渲染输出、丢帧和最后错误。诊断同时展示 H.264 profile、尺寸和实际选中的解码器。

默认使用系统选择的硬件 AVC 解码器。若海思解码器已接受配置和输入帧但在规定时间或帧数内没有任何输出，则释放硬解并使用 `OMX.google.h264.decoder` 重建。软件解码器不可用或性能不足时保留明确错误，而不是继续显示无原因黑屏。

## 状态刷新与诊断界面

后端维护单调递增的内容版本。父/子仓刷新、单仓增删和直播配置变化都会增加版本并清空相关首页、搜索和直播缓存。网页顶层持有该版本，源管理完成操作后立即更新；首页、搜索和直播页观察版本并重新拉取，不依赖固定 1.5 秒延迟。

网页设备页增加诊断区，包含：

- 上次 Java 崩溃和最后原生启动阶段；
- AirPlay 握手、视频包、解码器输入/输出及错误；
- 父仓、子仓、配置和逐站点健康状态；
- 最近网络请求的 HTTP/TLS 结果和直播缓存版本。

电视设置页只显示适合遥控器快速阅读的摘要和错误码，完整细节留在网页，避免挤占 1080p 电视界面。

## 测试策略

- JVM 单测覆盖 BOM/注释、单仓、多仓、去重、子仓差量同步、仓库延迟排序、Spider 摘要格式和 H.264 NAL 归一化。
- 网络单测使用本地 TLS 端点验证 API 19 TLS 1.2 Socket 配置和错误分类。
- Web 测试覆盖源版本变化后直播页重载、搜索切仓保留关键词和默认选择最快健康仓。
- API 19 x86 仪器测试覆盖冷启动和页面导航；ARM 构建检查 `armeabi-v7a` ELF 与 APK 内容。
- 真机验收必须使用 SHARP API 19 和 iPhone 16 / iOS 26.5.2，记录从连接到第一帧的诊断快照。模拟器无法证明海思硬解和新版 iOS AirPlay 兼容性。
